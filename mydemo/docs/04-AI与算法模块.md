## 二、NSGA-II 多目标智能路线规划

### 2.1 算法背景

NSGA-II（Non-dominated Sorting Genetic Algorithm II）是经典的多目标进化算法。在本项目中，算法需要在数百个景点候选中，找出在**多个冲突目标**间取得最优平衡的游览路线。

### 2.2 数据结构（nsga2_trip_planner.py）

```python
@dataclass
class ScenicSpot:
    name: str               # 景点名称
    city: str               # 所在城市
    area: str               # 所在区域
    tags: str               # 标签
    rating: float           # 评分（含季节加成）
    hotness: float          # 热度
    reviews: float          # 评论数（对数化后）
    cost: float             # 票价
    lon: float              # 经度
    lat: float              # 纬度
    center_distance_km: float  # 距市中心距离
```

### 2.3 核心函数详解

#### build_candidates(queryset, city, season) — 构建候选景点集

1. 从 TravelInfo 表过滤出指定城市景点（`city__icontains`）
2. 优先精确匹配（"上海" vs "上海市"）→ 精确匹配 ≥9 个就用精确结果
3. 解析每个景点的评分、热度、票价、坐标
4. 应用 `_season_bonus()` 给评分加季节匹配加成
5. 返回 `List[ScenicSpot]`

#### _evaluate_route(route_indices, spots, per_day) — 路线评价函数

计算一条路线的 5 个指标：
```python
{
    "cost": sum(各景点票价),                          # 越小越好
    "distance": 各景点距市中心 + 相邻景点Haversine距离,  # 越小越好
    "rating": mean(各景点评分),                        # 越大越好
    "hotness": mean(各景点热度),                       # 越大越好
    "reviews": mean(log1p(评论数))                     # 越大越好
}
```

#### NSGA-II 算法实现

**_fast_non_dominated_sort(population)** — 快速非支配排序
- 对每个个体统计被支配数（dom_count）和支配集合（dominated）
- 第0层（帕累托前沿）：无人支配的个体
- 第1层：仅被第0层支配的个体
- 依此类推

**_crowding_distance(population, front)** — 拥挤距离计算
- 在每个前沿内部，按每个目标函数排序
- 边界点赋予无穷大距离（保留）
- 内部点计算相邻解的目标差值之和
- 保持解的多样性

**_tournament(population)** — 锦标赛选择
- 随机选两个个体
- 先比 rank（非支配层级），rank 小的胜
- rank 相同比 crowding distance，大的胜

**_ordered_crossover(parent_a, parent_b)** — 有序交叉（OX）
- 随机选两个切点
- 从 parent_a 复制切点之间的基因
- 从 parent_b 按顺序填充剩余基因（跳过已存在的）
- 保证子代不重复

**_mutate(route, candidate_count, mutation_rate=0.2)** — 变异操作
- 交换变异（20%概率）：随机交换两个景点位置
- 替换变异（20%概率）：随机替换一个景点
- 调用 `_repair_unique` 修复重复

#### _evaluate_population(population, spots, per_day, budget) — 种群评估

对每个个体的 4 个优化目标：
```python
objectives = [
    cost,            # 最小化：总花费
    distance,        # 最小化：总路程
    -rating,         # 最小化：负评分（即最大化评分）
    -hotness,        # 最小化：负热度（即最大化热度）
]
```

**预算约束处理**：超出预算的个体赋予极大惩罚值 `[1e9+penalty, 1e9, 1e9, 1e9]`，确保它们被非支配排序淘汰。

#### run_nsga2(spots, days, budget, per_day=3, pop_size=40, generations=50) — 主算法

```
1. 初始化种群（随机生成路线）
2. 评估种群
3. 循环 generations 代：
   a. 非支配排序 + 拥挤距离
   b. 锦标赛选择 → 交叉 → 变异 → 生成子代
   c. 评估子代
   d. 合并父代+子代 → 精英选择 → 新一代种群
4. 返回第一前沿（帕累托最优解集）
```

默认参数：种群 40，进化 50 代（共 2000 次路线评估）。

#### choose_solution(pareto_set, sensitivities, budget) — 从帕累托前沿选择均衡解

根据用户在页面上调整的 5 个敏感性滑块权重，加权计算效用分数：

```python
utility = (
    price_sensitivity * normalized_cost      # 价格越高分越高
    + distance_sensitivity * normalized_dist  # 距离越长分越高
    - hotness_sensitivity * normalized_hot    # 越热门分越低
    - rating_sensitivity * normalized_rating  # 评分越高分越低
    + crowd_avoidance * normalized_crowd      # 越拥挤分越高
    + 0.15 * budget_gap                       # 预算偏离惩罚
)
```

选择 utility 最小的解作为均衡方案。

#### build_route_payload(best_solution, spots, days, per_day=3) — 构建前端需要的路线数据

将 NSGA-II 输出的整数索引数组转为结构化路线：
```json
[
  {
    "name": "外滩",
    "visit_time": "第1天-上午",
    "features": "黄浦区，评分4.8，热度9.2",
    "longitude": 121.490,
    "latitude": 31.240,
    "estimated_cost": "免费"
  }
]
```

额外处理：每日内部按 cost 降序排列（优先展示付费景点）。

### 2.4 视图层（views_nsga2.py）

#### generate_ai_nsga2_route(request) — POST API，生成路线

**处理流程**：
```
1. 解析 JSON 参数（city, season, days, budget, 5个敏感性权重）
2. 参数校验（城市非空、季节合法、天数>0）
3. build_candidates() 构建候选景点集
4. 检查缓存（相同参数是否在10分钟内生成过）
5. run_nsga2() 执行进化算法
6. _build_top3_options() 从帕累托前沿选出3个代表方案
   - economy：花费最低
   - balanced：效用最优
   - experience：评分+热度最高
7. 存入 PLAN_CACHE（10分钟TTL）
8. 返回 Top3 方案预览（不包含完整路线细节）
```

#### select_ai_nsga2_plan(request) — POST API，确认方案

用户选择一个方案后：
```
1. 从缓存取出完整路线数据
2. 检索知识卡片（JSON + Wiki RAG）
3. call_ai_refiner() → DeepSeek 生成攻略文本
4. call_ai_html_report() → 渲染 HTML 报告
5. 返回完整数据（路线 + 地图坐标 + AI文本 + HTML报告 + 知识卡片）
```

### 2.5 知识增强

#### JSON 知识卡检索（nsga2_knowledge.py）

`retrieve_knowledge_cards(city, route_data)` — 从本地 `travel_knowledge.json` 匹配路线中各景点的结构化知识（最佳时段、预约提示、避坑建议等）。

#### Wiki 知识卡检索（wiki_runtime_service.py）

`retrieve_wiki_knowledge_cards(city, route_data, season, budget)` — 从 Wiki 文件系统中检索与路线景点匹配的知识。

**匹配流程**：
1. 遍历所有 summary/*.md 页面
2. 按城市过滤（不匹配的跳过）
3. 对路线中每个景点名称做关键词匹配
4. 按季节和预算匹配度打分排序
5. 去重后返回 top-N 张知识卡

这种 RAG（检索增强生成）策略让 LLM 生成攻略时能引用本地的专业知识卡片，提升攻略的准确性和实用性。

### 2.6 AI 报告生成（nsga2_report.py）

#### call_ai_refiner(city, season, days, budget, route_data, knowledge_cards)

调用 DeepSeek 将结构化行程转为自然语言攻略文本。Prompt 要求：
- 按天分段
- 每个景点说明亮点
- 交通衔接建议
- 预算提醒和避坑建议
- 融入本地知识卡中的最佳时段和预约提示

#### call_ai_html_report(city, season, days, budget, route_data, metrics, knowledge_cards)

纯本地计算（不调用 LLM），将路线数据组织为 HTML 报告：
1. 按天分组景点
2. 计算每日花销和总花销
3. 生成交通衔接建议
4. 渲染知识卡片
5. 通过 Django `render_to_string("ksh/nsga2_report.html", context)` 渲染

## 三、LLM Wiki 知识库系统

### 3.1 系统架构

```
┌─────────────────────────────────────────────┐
│                    Wiki 知识库                │
│                                              │
│  raw/                 wiki/                  │
│  (原始文档)           (结构化知识)            │
│  ├── 上海攻略.md  ──→ summary/上海攻略.md    │
│                      entity/外滩.md           │
│                      concept/错峰出行.md       │
│                      cards/外滩.json          │
│                                              │
│  操作接口：                                   │
│  Ingest(摄入)  Query(查询)  Lint(检查)       │
└─────────────────────────────────────────────┘
```

### 3.2 核心思想

将非结构化的旅游攻略文档通过 LLM 编译为结构化 Wiki 知识网络：
- **摘要页（summary）**：每份 raw 文档的编译结果
- **实体页（entity）**：景点、餐厅等具体事物
- **概念页（concept）**：抽象标签（错峰出行、预算控制等）
- **知识卡片（cards）**：JSON 格式的结构化字段

### 3.3 摄入服务（wiki_ingest_service.py）

#### ingest_all_raw() — 批量摄入

```
1. 扫描 raw/ 目录下所有 .md/.txt 文件
2. 检查 .ingest_manifest.json 跳过未变化的文件（增量模式）
3. 对每个文件调用 ingest_raw_file()
4. 清理受 LLM 异常污染的 entity 页面
5. 刷新 index.md 索引
6. 写入日志
```

#### ingest_raw_file(raw_path) — 单文件摄入

```
1. 读取 raw 文件内容
2. 调用 WikiLLM.compile_raw() → LLM 编译
3. 写入 summary/{slug}.md
4. 创建/更新 concept 页面
5. 创建/更新 entity 页面（含结构化知识卡片）
6. 写入操作日志
```

**LLM 失败时的降级策略**（_normalize_compile_result）：
- 摘要 → 基于规则提取（extract_focus_lines）
- 概念 → 关键词正则匹配
- 实体 → 从标题中提取
- 知识卡片 → 生成基础占位卡片

### 3.4 查询服务（wiki_query_service.py）

#### query_wiki(question, city="") — 查询知识库

```
1. 遍历所有 summary/entity/concept 页面
2. 按城市过滤（如指定）
3. 关键词计数打分（text.lower().count(keyword)）
4. 取 Top-K 高分页面
5. 调用 WikiLLM.answer_query() → LLM 基于上下文生成答案
6. 调用 WikiLLM.rewrite_answer_for_user() → LLM 润色为自然语言
7. 返回：answer + 命中来源列表
```

**LLM 失败时的降级**：直接拼接命中页面的文件名和内容片段作为回答。

### 3.5 健康检查（wiki_query_service.py — lint_wiki）

1. 检查孤立页面（无交叉引用的页面）
2. 检查死链（引用 `[[...]]` 指向不存在的页面）
3. 检查摘要页面数量（少于2个则警告）
4. 评分：100 - 问题数 × 8（最低40分）

### 3.6 文件存储层（wiki_store.py）

所有 Wiki 数据存储在文件系统中：

| 函数 | 作用 |
|------|------|
| `ensure_dirs()` | 创建 wiki/ 及子目录 |
| `ensure_default_concepts()` | 初始化"错峰出行""预算控制"两个预设概念页 |
| `refresh_index()` | 自动生成 index.md |
| `format_summary_markdown()` | 格式化摘要页（加来源信息、交叉引用） |
| `upsert_entity_pages()` | 根据知识卡片创建/更新实体页 |
| `upsert_dynamic_concept_pages()` | 创建/更新概念页 |
| `sanitize_existing_entity_pages()` | 清理被 LLM 异常污染的实体页 |
| `append_log()` | 追加操作日志到 log.md |

### 3.7 文本提取工具（wiki_extract.py）

纯规则（不使用 LLM）的文本分析函数：

| 函数 | 作用 |
|------|------|
| `extract_title()` | 从 Markdown 标题提取页面标题 |
| `extract_focus_lines()` | 提取含"交通/门票/预约"等关键词的行 |
| `extract_month_signals()` | 正则提取"X月"信号 |
| `extract_spot_names()` | 从 `###` 标题和 `——` 分隔符提取景点名 |
| `extract_concepts()` | 关键词匹配识别概念标签（亲子出行/夜景路线/预约策略等） |
| `extract_pitfalls()` | 提取含"避雷/避坑/注意"等关键词的避坑建议 |
| `infer_best_time()` | 根据"夜景/上午"等关键词推断最佳时段 |
| `infer_budget_level()` | 根据"免费/低价/高价"等推断消费层级 |
| `infer_transport_mode()` | 根据"地铁/公交/打车"推断交通方式 |
| `infer_crowd_level()` | 根据"排队/极少"等推断人流密度 |
| `clean_text()` | 清理 LLM 异常标记 |
| `normalize_entity_name()` | 移除编号前缀，规范化实体名 |

### 3.8 LLM 封装（wiki_llm.py）

#### WikiLLM 类

所有调用统一使用 `extra_body={"thinking": {"type": "disabled"}}` 禁用 DeepSeek 的推理链思考，加快响应速度。

**compile_raw(raw_content, source_name)** — 文档编译

System Prompt 要求 LLM：
1. 深入理解原文，提炼隐含信息
2. 识别实体、概念标签
3. 建立交叉引用 `[[实体:xxx]]` `[[概念:xxx]]`
4. 为每个景点生成结构化知识卡片（14个字段）
5. 输出纯 JSON（不用 markdown 代码围栏）

**answer_query(question, pages)** — 知识库查询回答

将召回的 Wiki 页面作为上下文，要求 LLM 生成带来源引用的结构化答案。如果多个来源信息冲突，指出冲突并给建议。

**rewrite_answer_for_user(question, draft_answer, hits)** — 答案润色

将第一版回答整理成面向普通用户的自然语言，去除"Wiki页面""实体清单"等术语。

**lint_pages(pages)** — 健康检查

要求 LLM 检查：
1. 矛盾信息（A说免费，B说100元）
2. 过时信息
3. 遗漏交叉引用
4. 孤立页面
5. 信息空白

输出 JSON：`{"issues": [{"severity": "high/medium/low", "page": "...", "description": "..."}]}`
