# Agent 工作规范

## 1. 先规划，后动手（Plan 模式）

- 用户提出需求后，**必须先输出你的理解 + 执行计划**，等我确认或调整后再开始写代码。
- 计划里要说清楚：你要改哪些文件、大概怎么改、有没有风险。
- **绝对禁止**：理解完需求后直接开始修改代码、生成文件、覆盖内容。

## 2. 遇到麻烦，先问人，别硬扛

- 如果你发现某件事靠自己硬做会很麻烦、很绕、或者可能搞坏东西，**立刻停下来问我**。
- 典型情况：
  - 文件太大（比如超过 500 行），你的上下文或编辑器处理吃力。
  - 需要反复重试、多次重写才能搞定。
  - 只需要我手动删几行、改个配置，你就能轻松继续。
- **原则**：如果"问我一句话 + 我动一下手指"能帮你省掉 80% 的麻烦，那就必须问。

## 3. Git 兜底确认

- **动手改文件前，确认该文件已有 Git 追踪**（可以溯源、可以回滚），没有的话先问我。

## 4. 有问题先搭脚手架，别猜

- 遇到诡异问题（闪跳、样式不对、逻辑不执行），**先写诊断脚手架确认根因**，不要凭经验推测。
- 脚手架形式：MutationObserver 监控 DOM 变化、console.log 打时间戳追踪执行流、临时注释排除法。
- **原则**：先证明"问题是谁引起的、什么时候发生的"，再决定"怎么修"。没确诊就开药方是最浪费时间的做法。
- 修完后记得把脚手架删掉，不要留在代码里。

## 5. 代码组织原则（防屎山）

- **小文件优先**：单个代码文件尽量控制在 300 行以内。除非十几个函数是同一个工作流、拆开会反而难读，才可以放宽。
- **拆小函数**：一个函数干一件事，别一个函数写 100 行逻辑。
- **配置外置**：全局变量、可变的参数、环境相关的值，**写进 config 文件**，禁止硬编码在代码里。
- **命名直白规范**：变量名函数名让人一眼看懂，别用 a、b、tmp1 这种，或者是字段名使用拼音这种极不规范命名。
