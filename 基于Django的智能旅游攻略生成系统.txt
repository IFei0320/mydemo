摘  要
随着旅游业的快速发展和个性化出行需求的日益增长，传统旅游攻略在时效性、个性化和信息整合方面已难以满足当代游客的决策需求。静态攻略无法根据用户偏好、预算和时间安排动态适配，碎片化的旅游信息也缺乏有效的关联与检索机制，导致用户在行程规划中面临信息过载和决策困难的双重挑战。
针对上述问题，本文设计并实现了一套基于Django框架的智能旅游攻略生成系统，采用B/S架构与MySQL数据库，融合多目标优化算法与大语言模型技术。系统包含五大功能模块：用户管理模块提供注册登录、个人信息维护和头像上传等功能；数据可视化模块基于ECharts从评分分布、热度排行、价格分析和区域分布四个维度直观呈现旅游数据；智能攻略生成模块作为核心创新，先调用DeepSeek大语言模型生成城市概览，再以NSGA-II非支配排序遗传算法对行程成本、交通距离、景点评分和热度进行多目标优化，输出帕累托最优方案，并由大语言模型润色为包含每日行程、交通建议和预算明细的结构化报告，支持一键导出至滴答清单；Wiki知识库模块通过LLM驱动的结构化编译，自动抽取攻略文档中的实体、概念和知识卡片并建立交叉引用网络，在方案确认和报告生成阶段补充最佳时段、预约提示、交通建议和避坑信息。后台管理模块基于Django Admin对用户数据和景点数据进行统一维护，支持数据的增删改查操作。
测试结果表明，该系统能够较好地支撑个性化旅游攻略的生成，降低用户手工整理攻略的时间成本。为旅游推荐与智能行程规划系统的设计提供了可参考的实现方案。
关键词：旅游攻略生成；Django框架；NSGA-II算法；大语言模型；检索增强生成

Abstract
With the rapid development of the tourism industry and the growing demand for personalized travel, traditional travel guides have become inadequate in meeting the decisionmaking needs of contemporary tourists in terms of timeliness, personalization, and information integration. Static guides cannot dynamically adapt to users’ preferences, budgets, and schedules, while fragmented travel information lacks effective association and retrieval mechanisms, leaving users facing the dual challenges of information overload and decision difficulty during trip planning.
To address these issues, this paper designs and implements an intelligent travel guide generation system based on the Django framework. The system adopts a B/S architecture and a MySQL database, integrating multiobjective optimization algorithms with large language model (LLM) technologies. It comprises five functional modules. The user management module provides registration, login, personal information maintenance, and avatar upload. The data visualization module uses ECharts to present travel data from four dimensions: score distribution, popularity ranking, price analysis, and regional distribution. As the core innovation, the intelligent guide generation module first invokes the DeepSeek LLM to generate a city overview, then applies the NSGA-II nondominated sorting genetic algorithm to perform multiobjective optimization on travel cost, transportation distance, attraction rating, and popularity, producing Pareto optimal solutions. The results are then polished by the LLM into a structured report containing daily itineraries, transportation suggestions, and budget details, with oneclick export to TickTick. The Wiki knowledge base module employs LLMdriven structured compilation to automatically extract entities, concepts, and knowledge cards from guide documents and build a crossreferencing network, supplementing optimal visiting times, reservation tips, transportation advice, and pitfallavoidance information during solution confirmation and report generation.The backend management module utilizes Django Admin to centrally manage user and attraction data, supporting all essential data operations—including addition, deletion, modification, and querying.
Test results show that the system effectively supports the generation of personalized travel guides, reduces the time cost of manual guide compilation for users, and provides a reference implementation for the design of travel recommendation and intelligent itinerary planning systems.
Keywords: travel itinerary generation; Django framework; NSGA-II algorithm; large language model; retrieval-augmented generation

第一章 绪论
1.1 项目背景及研究意义
1.1.1 项目背景
近年来，居民生活水平持续提升，旅游已成为日常消费和节假日出行的重要内容。国内旅游市场总体保持恢复增长，出游人次和旅游消费规模持续扩大[1]。旅游需求增长的同时，人们对行程安排的要求也在不断提高，从单纯关注目的地选择转变为对行程整体优化决策的重视，旅游路线规划已成为一个需要综合权衡时间、空间、费用和个人偏好的决策问题。
实际出游时，用户需同时考虑景点位置、交通方式、门票价格、热门程度、季节因素及预约规则等诸多内容，尤其在热门城市或短期出游场景下，用户需从大量攻略和游记中自行筛选信息，不仅费时费力，还容易出现路线重复、预算超支或景点安排不合理等问题。现有旅游平台主要解决信息检索与产品预订问题，在路线智能规划方面的支持仍显不足[2]。
旅游路线规划具有明显的多目标特点：用户希望预算可控、路程少、景点质量高且体验符合偏好，但这些目标并不完全一致，多目标优化方法为此提供了可行的技术路径。同时，智能问答与文本生成技术虽能快速生成行程建议，但完全依赖该方法容易出现内容不准确或对预算、时长等条件考虑不充分的问题[3]。可见，单一方法难以满足真实需求。因此，结合多目标优化与用户特征建模的路线推荐方法具有一定研究价值[4]，而在此基础上进一步引入知识补充与文字说明，有助于提升路线结果的实用性和可读性。
1.1.2 研究意义
从理论层面看，本研究将旅游推荐的重心从“推荐哪些景点”拓展至“如何串成一条可行路线”，尝试将预算、距离、评分、热度及开放时段等多维约束纳入统一的分析与优化框架，有助于丰富旅游推荐问题的建模方式。同时，将多目标优化算法与大语言模型知识增强机制相结合，为旅游路线规划领域提供了一种“结构化求解 + 知识注入 + 自然语言输出”的技术范式，对推动推荐系统从单一排序向综合决策的方向延伸具有一定参考价值。
从实践层面看，本研究直接回应用户在制定旅游攻略时面临的信息过载与行程编排缺乏系统性难题。通过NSGA-II算法生成兼顾成本、距离和质量的多目标帕累托最优方案，再借助知识卡片匹配机制补充时段、预约规则、交通建议及避坑提示等实用信息，最后以大语言模型输出良好可读性的结构化行程说明，使规划结果在合理性与易用性之间取得平衡。该方案可为在线旅游平台和个性化出行辅助系统提供一种可落地的实现思路，在保证方案质量的同时，弥补现有方法在信息丰富度和可读性方面的不足，从而更好地衔接智能规划结果与用户的实际出行决策。
1.2 国内外研究现状
1.2.1 旅游推荐系统研究现状
旅游推荐系统的核心任务是根据用户兴趣、行为及景点特征推荐合适的旅游对象。早期以协同过滤和基于内容的推荐为主，随后引入上下文信息和混合推荐机制，提升了推荐的准确性和个性化程度。然而，现有研究多聚焦于“推荐什么”，对“如何串成完整路线”关注较少。推荐系统能给出值得去的景点，却难以处理景点间的时间衔接、空间顺序和预算约束，而用户真正需要的是可直接执行的行程。因此，将推荐与路线规划相结合已成为该领域的重要方向。
1.2.2 多目标优化在旅游路线规划中的应用
旅游路线规划本质上是在多种约束下完成景点的选择与排序，遗传算法、蚁群算法、粒子群算法及多目标进化算法已被先后引入，其中NSGA-II因能同时处理多个冲突目标而受到较多关注[5]。已有研究表明，多目标优化在兼顾成本、距离、时间和满意度方面比简单排序更贴近实际需求，但仍存在不足：部分研究停留在仿真层面，与真实数据和场景结合较弱；偏重算法性能而忽视结果的可理解性；对预约、时段、拥挤等非结构化知识利用不足。因此，在多目标优化基础上引入知识补充机制值得深挖。
1.2.3 智能生成方法与知识增强研究趋势
近年来，智能问答与文本生成技术在旅游服务中的应用逐渐增多，能直接理解自然语言输入并生成行程建议，交互体验有明显优势。但缺少外部知识支撑时，容易给出与真实开放时间不符或忽略预算等关键约束的建议。为弥补这些不足，研究者开始引入知识图谱、检索增强生成（RAG）和本地知识库等方法[6]。在旅游场景中，最佳游览时段、购票方式、交通贴士等知识属性强，适合作为路线结果的补充。总体来看，旅游推荐、路径优化和文本生成各自取得了一定进展，但三者之间的结合仍很不够，将多目标优化、知识补充与行程说明统一起来，形成面向真实场景的旅游路线规划系统，仍具有重要研究价值。
1.3 研究内容
针对现有旅游推荐难以直接形成完整路线、传统路径优化缺少知识补充、智能生成方法结果不够稳定等问题，本文围绕智能旅游路线规划系统的设计与实现展开研究。目标是：在用户给出城市、季节、预算、天数和偏好的基础上，自动生成兼顾成本、距离、评分与热度的旅游路线，并利用本地知识库和 Wiki化资源对路线结果进行补充说明。
具体工作包括：第一，构建旅游景点结构化数据，整理本地旅游知识卡片与原始攻略资料，为路线规划打好数据基础；第二，采用 NSGA-II 多目标进化算法生成多组有代表性的候选路线方案；第三，设计知识命中与筛选机制，将景点相关的最佳时段、预约提示、交通建议和避坑经验补充进路线结果；第四，对结构化结果进行文字化处理，使输出便于用户理解；第五，完成系统实现与功能验证，评估该方案在旅游路线规划任务中的实际效果。

第二章 关键技术介绍
2.1 Django Web框架
Django是Python生态中一款成熟的Web开发框架，具有开发效率高、结构清晰、易于维护的特点[7]。本系统选用Django 4.2.16作为后端框架，主要基于其文档完善、功能齐全，能够有效支撑旅游路线规划系统中的数据管理、业务逻辑处理和页面交互需求。
Django采用MTV架构模式，即Model负责数据结构与数据库的映射，Template负责页面渲染，View负责请求处理与业务逻辑，使系统各层职责清晰。其内置ORM机制允许开发者通过Python类完成数据库操作，避免了大量手写SQL的工作；路由系统便于各功能模块独立组织；中间件机制则有利于统一实现日志记录、权限控制等通用功能。综上，Django能够较好地满足本系统快速开发与后续维护的需求。
2.2 多目标优化与NSGA-II算法
旅游路线规划本质上是一个多目标优化问题。用户在安排行程时通常希望在预算可控的前提下减少路程、提高景点评分、优化整体体验，但这些目标之间往往相互牵制，无法用单一指标衡量。多目标优化问题的一般形式如式（2-1）所示：

本系统设定四个优化目标：总门票成本最低、景点间总路程最短、平均评分最高、平均热度最高。评分和热度在计算时转化为最小化负值以统一求解方向，同时路线需满足预算、出游天数和同城约束。NSGA-II先根据城市筛选候选景点生成初始种群，计算每条路线在花费、距离、评分和热度上的表现，再通过非支配排序、选择、交叉和变异反复迭代，最终得到一组Pareto候选解，并整理为省钱型、均衡型和体验型等不同风格的方案。相比简单排序方法，该算法能更有效地兼顾多个目标，更适用于旅游路线规划问题[8]。
2.3 检索增强生成（RAG）
在旅游路线规划系统中，完全依赖模型直接生成结果容易出现内容不准确或依据不足的问题。检索增强生成（RAG）的核心思路是“先检索，再生成”——先从外部知识中找出相关信息，再将这部分内容作为补充融入结果整理过程。
本系统的知识增强采用了轻量化的实现方式，未引入向量数据库，而是基于本地Markdown Wiki、JSON知识卡片和关键词匹配规则来完成检索。系统根据城市和路线涉及的景点进行匹配，提取出最佳游览时段、预约建议、交通提示和避坑信息。这种方式虽然在语义检索的灵活性上不如标准RAG，但实现更简便，也更能适配当前系统的实际需求[9]。
2.4 MySQL数据库
MySQL是一种广泛应用的开源关系型数据库管理系统。本系统选择MySQL作为数据存储方案，主要基于以下几点考虑：它性能稳定可靠，支持灵活的事务处理，提供丰富的数据类型和功能，同时具备良好的安全性与高可用性。无论是小型Web应用还是大型企业级系统，MySQL都能提供高效、稳定的数据存储与管理服务。在本系统中，MySQL主要负责存储用户信息、景点数据和可视化预计算结果；路线方案在生成阶段暂存于服务端内存缓存中，未进行关系型数据库持久化，与Django的ORM机制配合使用，开发效率较高。

本章介绍了系统实现所涉及的相关理论与关键技术。首先说明了Django Web框架在系统开发中的基础作用，随后重点分析了多目标优化问题及NSGA-II算法的原理，并结合旅游路线规划场景给出了建模思路，最后介绍了检索增强生成的基本思想及本系统的轻量化实现方式。这些内容为后续系统的设计与实现提供了理论和技术基础。

3.3 功能需求分析
系统旨在为用户提供从旅游数据浏览、可视化分析到个性化行程规划的一站式服务，采用B/S架构，后端基于Django框架，前端使用Bootstrap和ECharts，整体划分为用户管理、旅游数据可视化、智能攻略生成、Wiki知识库和后台管理五个模块。
3.3.1 用户管理模块
用户管理模块负责系统用户的注册、登录、身份认证和个人信息维护。注册时对用户名和邮箱做唯一性校验，密码经哈希加盐处理后入库，避免明文泄漏；登录成功后系统创建会话并写入用户标识，有效期14天，以保证访问连续性。个人信息页面支持用户名、邮箱、手机号、地址和邮编的修改，同样对用户名和邮箱做唯一性校验；头像上传限制为常见图片格式且不超过2MB，以“用户标识+时间戳”组合命名后存入服务端媒体目录。退出登录后会话清除并返回登录页面。该模块是系统运行的基础入口。
3.3.2 旅游数据可视化模块
旅游数据可视化模块对景点数据进行统计分析与展示。首页以仪表盘形式展示收费景点数、覆盖省份数、城市数和评论总量，并通过地图展示景点分布。专题分析从评分、热度、价格和区域分布四个维度进行可视化，并支持按名称、省份等条件查询和分页浏览，帮助用户在出行前对目标旅游资源形成全面认知。

3.3.3 智能攻略生成模块
智能攻略生成模块是系统的核心模块。用户输入城市、季节、预算、出行天数后，系统先调用大语言模型生成目的地概览并结合景点经纬度在地图上展示候选分布。路线优化阶段，用户进一步设置价格敏感度、距离容忍度、热度偏好等参数，系统筛选候选景点集合，使用NSGA-II算法从成本、距离、评分和热度四个目标进行多目标优化，返回Top3候选方案。用户确认方案后生成路线地图、统计指标、AI文本攻略[11]和HTML报告，并支持导出至滴答清单。
3.3.4 Wiki知识库模块
Wiki知识库模块负责原始资料的摄入、组织、查询和复用，为智能攻略生成提供知识支撑。管理员将原始Markdown或文本资料放入指定目录后，系统自动完成摘要生成、实体抽取和概念提炼，构建结构化知识库[12]。系统可根据城市和景点名称检索知识卡片并应用于路线生成和报告输出，同时支持自然语言查询生成带来源标注的回答，并提供健康检查功能，检测引用缺失和孤立页面等问题。
3.3.5 后台管理模块
后台管理模块面向管理员，依托 Django Admin 对用户数据和景点数据进行统一维护；Wiki 内容则通过专门的 Wiki 知识库页面完成文档摄入、查询和健康检查。管理员可完成数据维护和知识更新操作，保证后台数据能够及时反映到前台检索、分析和路线生成等业务中。
3.4 非功能性需求
本系统在功能实现之外，还需满足性能、安全性、可扩展性、可维护性及用户体验五个方面的质量约束。结合旅游路线规划场景的具体特点，各项要求如下。
（1）性能需求。 路线规划涉及NSGA-II种群迭代优化与LLM调用，计算开销较大。系统要求单次路线生成请求的响应时间不超过30秒，其中NSGA-II计算控制在15秒以内，LLM调用采用异步与超时重试机制，避免阻塞用户请求。前端页面首屏加载时间不超过3秒，静态资源启用缓存策略。数据库查询需对高频字段建立索引，分页列表查询响应控制在500毫秒以内。
（2）安全性需求。 用户认证采用会话机制，会话标识通过仅限 HTTP 的 Cookie传输，防止客户端脚本窃取。登录密码经哈希加盐存储，杜绝明文泄露。所有视图函数均须进行登录状态校验，未认证请求重定向至登录页。文件上传限制允许的内容类型与大小，防止恶意文件注入。SQL查询统一使用Django ORM参数化方式，消除SQL注入风险。
（3）可扩展性需求。 系统采用Django MTV分层架构，视图、模型与模板解耦。NSGA-II引擎、LLM客户端与Wiki知识库引擎均封装为独立模块，通过统一接口与视图层交互，便于替换底层算法或模型。滴答清单导出通过独立视图实现，新增第三方平台对接时仅需新增适配模块。
（4）可维护性需求。 代码遵循PEP 8规范，关键函数附带中文注释说明算法逻辑。配置项集中于settings模块管理，避免硬编码。算法模块提供独立的单元测试用例，覆盖候选集构建、距离解析、NSGA-II收敛验证与方案比较等核心路径。
（5）用户体验需求。 界面采用响应式设计，适配桌面端与移动端浏览。路线方案以可视化地图配合指标对比卡片呈现，支持一键切换经济型、平衡型与体验型三种方案。知识卡片与AI报告以结构化面板展示，降低用户信息获取成本。操作流程保持三步以内完成核心任务，交互反馈及时明确。

5.3 NSGA-II算法核心设计
5.3.1 算法核心流程
NSGA-II（Non-dominated Sorting Genetic Algorithm II）是本系统路线规划模块的核心优化引擎[17]。算法以候选景点列表为搜索空间，以染色体编码表示景点选择与排列方案，通过快速非支配排序和拥挤距离机制在四个优化目标之间搜索Pareto最优解集[18]。算法整体流程如算法5-1所示：
1.  输入：候选景点列表 spots，行程天数 days，预算上限 budget，
2.        每日最多景点数 per_day，种群大小 pop_size，最大进化代数 generations
3.  输出：Pareto 最优解集（可行行程方案）Π*
4.  route_len ← min(days × per_day, |spots|)
5.  P ← 初始化种群（pop_size, route_len）
6.  计算种群 P 的适应度与约束违反度（spots, budget）
7.  for gen ← 1 to generations do
8.      F ← 快速非支配排序（P）
9.      for each front f in F do
10.         计算 f 中个体的拥挤距离
11.     end for
12.     Q ← ∅
13.     while |Q| < pop_size do
14.         p1 ← 锦标赛选择（P）
15.         p2 ← 锦标赛选择（P）
16.         c ← 有序交叉（p1.染色体， p2.染色体）
17.         c ← 变异（c, |spots|）
18.         Q ← Q ∪ {c}
19.     end while
20.     计算种群 Q 的适应度与约束违反度（spots, budget）
21.     R ← P ∪ Q
22.     P ← 精英选择（R, pop_size）
23. end for
24. F1 ← 快速非支配排序（P）的第一前沿
25. Π* ← {x ∈ F1 | x 满足所有约束｝
26. return Π*

（4） 有序交叉（OX）
有序交叉适用于排列编码，保证子代无重复基因。步骤：
　　　（a） 从父代A随机截取子序列，直接复制到子代对应位置；
　　　（b） 遍历父代B，跳过已选基因，将剩余基因按原序填入子代空位。
（5） 变异算子
由两个子操作组成，各自以0.2概率触发：
　　　（1） 交换变异——随机交换两个位置的基因；
　　　（2） 替换变异——随机替换某位置为未出现的点。变异后函数消除重复。
（6） 精英选择
合并父代与子代种群（规模2N），先进行非支配排序，再按前沿层级从低到高依次选取整层个体。对最后一个可部分入选的前沿，按拥挤距离降序截取所需数量，确保历代最优解不丢失。参数配置如下表5-1所示：

5.5 数据分析模块详细设计
数据分析模块由｀ksh｀应用承载，其设计原则是“查询与渲染分离”：Django视图函数负责从MySQL查询数据并进行Python层面的聚合计算，前端ECharts负责将聚合结果渲染为可交互的图表。视图函数返回的页面中，聚合数据以JSON格式通过Django模板的｀mark_safe｀过滤器注入JavaScript变量，ECharts在页面加载时读取这些变量并调用对应的图表初始化函数。

5.6 Wiki知识库模块详细设计
在摄入流程中，系统扫描 raw/ 目录下的 Markdown 或文本文件，将其交由 LLM 生成摘要、实体、概念和知识卡片，并写入 wiki/summary/wiki/entity/wiki/concept/ 与 wiki/cards/ 等目录；在查询流程中，系统先根据关键词召回相关页面，再将页面内容提供给 LLM 生成带来源标注的回答。若模型调用失败，系统通过规则化摘要与关键词匹配机制提供基础兜底结果。整体上，该模块采用“LLM 生成 + 规则兜底”的双轨机制：优先利用大语言模型完成结构化理解，当模型调用异常或结果解析失败时，系统通过规则化摘要和关键词匹配维持基础可用性。

本章在总体设计的基础上对各功能模块进行了详细设计。基于Django的MTV模式完成类图与时序图设计，明确了各层职责与交互关系；阐述了用户模块的Session认证、头像上传校验及信息维护流程；重点设计了NSGA-II多目标优化引擎，通过快速非支配排序、拥挤距离计算、锦标赛选择、有序交叉与精英保留等核心算子，在行程成本、交通距离、景点评分与热度四个优化目标之间搜索Pareto最优解集；在此基础上设计了路线规划模块中NSGA-II引擎、LLM客户端与Wiki知识库引擎的协同时序流程；数据分析模块采用“查询与渲染分离”原则，前端ECharts渲染并设计了自适应降级策略；Wiki知识库模块以独立于Django的双轨机制保障知识摄入的鲁棒性。以上设计为后续系统实现提供了工程依据。

7.6 算法性能实验
为评估NSGA-II算法在旅游路线规划任务中的实际表现，本节设计了三组实验：算法对比实验、收敛性分析和参数敏感性分析。实验数据集为上海市200条有效景点记录，测试场景为3天行程、每日3个景点（共9个景点）、预算280元。NSGA-II参数配置为种群大小40、进化代数50、交叉概率0.8、变异概率0.2。
7.6.1 算法对比实验
将本文实现的NSGA-II算法与两种基准策略进行对比：
贪心算法（Greedy）：按评分降序遍历景点，在累计成本不超过预算的前提下选取 route_len 个景点。受限于紧预算，当剩余资金不足以选取后续高评分景点时提前终止，可能无法填满全部行程。
随机算法（Random）：从候选景点中随机选取9个不重复景点，重复生成1000次，取其中成本最低的一组。
三种算法的对比实验结果如表7-6所示。
表7-6 不同算法在上海3天行程下的对比结果
算法	总成本（单位：元）	总路程（单位：km）	平均评分	平均热度	运行时间（单位：s）	Pareto解数
NSGA-II（本文）	243.12	126.7	4.70	6.49	0.97	38.8
贪心算法（Greedy）	279.0	14.6	4.90	4.57	<0.01	1
随机算法	450.64	251.0	4.51	5.95	0.02	1
（1） 成本优化：NSGA-II平均总成本为243.12元，在预算约束线（280元）以内，可行率100%。贪心算法因紧预算限制（280元仅略高于9景点最低成本约151元），仅能选出少数高评分景点，在8次运行中均无法填满9个行程且可行率为0%。随机算法平均成本450.64元，超预算约61%。这表明在紧预算约束下，简单贪心策略无法在填满行程与满足预算之间取得平衡，随机策略也无有效约束处理能力。NSGA-II则在种群进化过程中将成本作为显式优化目标纳入非支配排序，通过全局搜索在成本与体验间取得了有效平衡。
（2） 路程优化：贪心算法因紧预算限制（280元），仅能选出3个高评分景点即耗尽预算，无法完成9景点行程，实际不可用。随机算法虽选满9景点，但平均成本450.64元（超预算61%）。NSGA-II是唯一同时满足“9景点满行程”和“预算≤280元”的方法。
（3） 多解优势：NSGA-II平均输出38.8个Pareto最优解（单次运行约33—40个），覆盖省钱型（约208元/4.63分）到体验型（约274元/4.72分）多种方案。贪心和随机均仅输出单一解且存在根本性缺陷（行程不完整或超预算）。NSGA-II的多解能力使用户可以在满足所有约束的前提下，根据偏好自由选择路线风格。
（4） 运行时间：NSGA-II平均耗时0.97秒，虽高于贪心（<0.01秒）和随机（0.01秒），但完全在Web交互的可接受响应范围内。考虑到其单次运行即可产出约39个高质量候选方案，且是三种算法中唯一能同时满足预算约束和行程完整性的方法，这一计算开销是值得接受的。
图7-1展示了NSGA-II在两个目标空间中的Pareto前沿分布。图（a）中Pareto前沿呈现出成本与评分之间的权衡关系——成本从207.8元增至240元时评分提升相对明显（4.633→4.689），但从223元增至273.9元时评分提升趋缓（4.689→4.722），说明在中低预算区间增加投入即可获得较好的体验回报，超过一定阈值后边际收益递减。三个标注点（省钱型207.8元/4.633分、均衡型223.8元左右/4.689分、体验型273.9元/4.722分）覆盖了前沿的不同成本区间，在280元预算约束下为不同偏好的用户提供了清晰的决策参考。图（b）展示了成本与路程的权衡关系，总路程范围为68.8—248.2 km，低成本方案通常集中游览邻近景点，路程相应较短，这与直观经验相符；但路程与成本之间并非严格正相关，部分高评分景点地理位置分散，导致路程随成本增长存在一定波动。

第八章 结论和展望
8.1 工作总结
本文设计并实现了一个基于 Django 的旅游数据分析与智能路线规划平台，将数据采集清洗、多维度可视化分析、大语言模型攻略生成与多目标进化优化算法有机整合为完整的技术链路。
在数据层面，系统通过携程 API 爬取全国景点信息，经过去重、清洗与结构化存储，构建了覆盖多个省份与城市的旅游数据库，并预计算了评分分布、热度排行、价格区间等多组离线分析表，为上层可视化与分析提供高效数据支撑。
在分析层面，平台以 ECharts 交互式图表为载体，提供了评分、热度、票价、区域分布四个维度的可视化分析功能。其中门票价格分析采用“汇总－详情”双模式设计，区域分布分析实现了三层自动降级策略，有效应对了原始数据粒度不均的现实问题。
在智能规划层面，本文将旅游路线规划建模为多目标优化问题，引入 NSGA-II 算法在成本、路程、评分、热度四个冲突目标之间寻求帕累托最优解集。算法实现包含快速非支配排序、拥挤距离保持、有序交叉与精英保留策略，种群规模 40、进化 50 代，从数百个候选景点中高效筛选出最优路线组合。在此基础上，系统自动从帕累托前沿中提炼节省型、均衡型与体验型三个代表性方案，以可视化卡片形式呈现给用户，赋予用户在不同偏好之间的选择权，体现了“人机协同决策”的设计理念。
在知识增强层面，系统构建了 LLM Wiki 知识库，将非结构化的旅游攻略文档通过大模型编译为摘要页、实体页、概念页与结构化知识卡片，形成可检索的知识网络。在路线生成时以 RAG 方式检索相关知识，使 LLM 生成的攻略文本与 HTML 报告能够引用本地的专业知识，提升了内容的准确性与实用性。
最后，系统支持将选定的路线方案一键导出至滴答清单，每个景点自动创建为独立任务并设定时间与提醒，打通了从规划到执行。
8.2 不足与展望
本系统仍存在若干值得改进的方向：
数据实时性方面，当前景点数据依赖一次性爬取与离线预处理，缺乏自动化的增量更新机制。未来可引入定时爬取任务与变化检测，使数据库保持与源站同步的时效性。
算法扩展性方面，NSGA-II 的实现为单机同步运算，当候选景点规模扩大到跨城市、跨省份时，计算时间将显著增长。后续可探索并行化种群评估、引入 NSGA-Ⅲ 处理超多目标场景，或将预训练的景点嵌入向量融入初始化种群以加速收敛。
数据方面，当前数据库部分数值型字段（rating、actual_price、popularity_score 等）因源自爬虫原始数据而以 VARCHAR 类型存储，虽在算法执行层通过 _safe_float 等清洗函数统一完成类型转换，不影响计算正确性，但若在 ETL 入库阶段完成字段规范化并改为 DECIMAL/FLOAT 类型，将有助于提升数据质量并支持 SQL 层直接聚合查询。
知识库方面，当前 Wiki 系统依赖文件存储与关键词匹配检索，召回精度受限。未来可引入向量数据库与语义检索，将知识卡片的匹配从字面提升到语义层面，并支持多轮对话式的交互查询。
个性化方面，当前系统使用统一的敏感性权重滑块让用户表达偏好，但缺乏对用户历史行为的学习能力。后续可引入用户画像建模与协同过滤推荐，使路线规划从“千人一面”走向“千人千面”。
